# Decision 005: Visit Negotiation Policies

**Date**: 2026-10-12  
**Status**: Approved by user for specification and planning; implementation remains proposed  
**Scope**: `specs/004-negotiate-visit-slots/` and synchronized binding policy clauses in `BUSINESS_RULES.md`

## Context

Feature 004 needs deterministic rules for participant availability, priority and tentative holds, consent, no-common-time outcomes, silence, and terminal representation. Existing code is an earlier baseline and does not yet implement the negotiated workflow. This decision records the user's answers so the feature specification and plan contain no open policy blockers.

## Decisions

1. **Tenant-first candidates**: First ask the tenant for all explicit availability intervals. Merge overlapping/adjacent windows into their union, then split each union interval into consecutive two-hour blocks starting at its start and ignore residuals shorter than two hours. Do not invent fixed-grid slots, calendar availability, or handyman availability. Then ask the handyman about candidates surviving shared-agenda pre-filtering. The handyman may explicitly counter-propose a different full two-hour interval only when fully contained in the tenant's original interval union; the schedule authority pre-filters it, then tenant must confirm that exact slot. This is evidence and a proposal, not consent. Check all intervals for overlap across arbitrary starts.
2. **Pre-filter and transfer**: Before asking the handyman, check each tenant candidate against the shared agenda. A candidate occupied by an equal/higher urgency tentative hold or a confirmed visit is immediately returned to the tenant for an alternative/all availability. Free or strict-higher-urgency-preemptible candidates may be sent to the handyman. A transfer happens atomically only after the requester explicitly selects/authorizes the candidate. Transfer all overlapping lower-urgency holds together; any equal/higher hold or confirmed appointment denies the whole transfer. Notify displaced tenants in their language and offer the earliest already-known common eligible block by UTC start then stable slot ID, otherwise renegotiate.
3. **Two-party consent**: Availability is not consent. Ask tenant and handyman for explicit yes/no against the same immutable proposal ID/version. A prior acceptance may be reused only for that exact version. A typed interpreter returns `yes`, `no`, or null plus `clarification_required`; it never coerces ambiguity. Bind decisions to the unique outstanding role question and current state, proposal, and schedule versions. Since stdin has no correlation fields, ambiguous delayed yes requires full-slot reconfirmation; perfect delayed-message disambiguation is not claimed.
4. **Terminal type and finalization**: The only terminal statuses are `scheduled` and `requires_review`, represented by a closed `TerminalStatus(StrEnum)` with exactly `SCHEDULED="scheduled"` and `REQUIRES_REVIEW="requires_review"`. It is nullable until terminal. Graph cursors and pending actions are separate. Atomic scheduled commit sets the immutable appointment, `terminal_status=SCHEDULED`, and `finalization_pending=true`. Review closure is atomic and mutually exclusive with commit. Confirmations are sent sequentially/idempotently before the scheduled terminal frame; failure retains the committed appointment and pending finalization without a premature frame. Delayed messages cannot change a terminal status.
5. **No eligible slot or no common time**: Before handyman questions, pre-filter tenant candidates against the shared agenda. If every requested candidate is blocked, ask for alternatives or all availability without querying the handyman about blocked slots. Once the tenant confirms that set is exhausted and no contained handyman counterproposal remains to evaluate, offer human scheduling; yes closes as `requires_review`, no requests new availability, and ambiguity gets clarification. This establishes `no_eligible_slot` from the complete tenant set plus known blockers even if handyman availability is unknown. Separately, known complete tenant and handyman evidence, including contained counterproposals, that proves no common eligible interval triggers the same question; partial/unknown handyman evidence alone is not proof of no common time and requires missing information.
6. **No-response**: Exact incoming body `<NO RESPONSE>` from tenant or handyman immediately closes an unfinished order as `requires_review`, with no retry and no approval. Prefix, suffix, or whitespace variants do not match. It cannot alter an already committed scheduled result. Provider/transport errors are not human absence.
7. **Language, reversals, and time**: Tenant language is scoped by `(work_order_id, role)` and includes supported recognized languages such as Spanish and English; handyman remains Spanish. Availability reversals from either party require sender confirmation: preserve the old value but suspend the disputed interval until resolved. Use UTC internally and approved `LOCAL_TIMEZONE` for display, defaulting to `Europe/Madrid`; add no relative-date or DST policy. Clarify ambiguous local time; defer a two-hour interval crossing a DST transition to authorized human review under the existing unresolved policy.

## Architectural Baseline and Branch Exception

The accepted continuation context is feature 003 because its graph baseline is not yet present on `develop`. This is a documented exception to the normal start-from-develop workflow, not a claim that feature 003 has merged. CodeGraph baseline evidence: startup invokes the language/initialization graph but discards its returned state; inbound messages go to a separate injected echo node. The current graph ends after recognition and fixed-Spanish initialization. The stdout writer serializes message blocks but has no terminal writer; JSONL trace writes are serialized. Feature 004 planning therefore includes retaining graph state, replacing the inbound echo route, and adding typed terminal frame writing.
